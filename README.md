# Veilance Telemetry API

> **Development Status:** This project is under active development. Several authentication, user, administration, and payout endpoints are currently placeholders and should not be considered production-ready.

The **Veilance Intelligence Network API** is the backend ingestion API used by the Veilance browser extension.

It currently provides public telemetry ingestion, client IP discovery, Redis-backed request rate limiting, API namespace separation for public/user/admin functionality, SQL-backed telemetry storage, and the initial structure for future authentication and payout functionality.

## Current Features

* Flask-based REST API
* Versioned public API under `/api/v1`
* Versioned user API under `/api/users/v1`
* Versioned administrative API under `/api/admin/v1`
* API information/status endpoint
* Client IP discovery
* Gzip-compressed telemetry uploads
* Multipart telemetry ingestion
* Basic telemetry JSON validation
* Wallet address support
* Client/contributor identifier support
* Domain-based telemetry deduplication
* SQL-backed telemetry storage
* Redis-backed distributed rate limiting
* Client ID-based rate-limit identities
* IP-based rate-limit fallback
* Standardized Veilance JSON API responses
* Global `429` rate-limit handling
* Global `500` exception handling
* Initial authentication endpoint structure
* Initial payout endpoint structure

# Upload Telemetry

```http
POST /api/v1/telemetry/upload
```

Telemetry is uploaded using:

```text
multipart/form-data
```

The endpoint currently reads the following form fields:

```text
ip_address
client_id
wallet_address
domain_name
telemetry
```

The `telemetry` field must be an uploaded gzip-compressed JSON file.

### Required by the current implementation

The endpoint explicitly rejects uploads when the following are missing:

```text
telemetry
wallet_address
domain_name
```

`client_id` and `ip_address` are read from the request and passed to the backend but are not currently explicitly rejected when empty by the upload handler.

---

## Example Upload

```bash
curl -X POST \
  -F "ip_address=127.0.0.1" \
  -F "client_id=example-client-id" \
  -F "wallet_address=example-wallet-address" \
  -F "domain_name=example.com" \
  -F "telemetry=@telemetry.json.gz;type=application/gzip" \
  http://127.0.0.1:5132/api/v1/telemetry/upload
```

A successful upload returns data equivalent to:

```json
{
  "output": {
    "ok": true
  }
}
```

The exact response envelope is controlled by:

```python
settings.build_json_report()
```

# Telemetry Format

After gzip decompression, the uploaded file must contain valid JSON.

The current top-level telemetry structure is expected to contain:

```json
{
  "schemaVersion": "veilance.telemetry-snapshot-batch.v1",
  "batchId": "example-batch-id",
  "contributorId": "example-contributor-id",
  "observations": []
}
```

The current validator checks for the existence of these four top-level fields:

```text
schemaVersion
batchId
contributorId
observations
```

The validation logic currently does **not** perform full schema validation.

For example, it does not currently enforce:

* Specific `schemaVersion` values
* Data types
* Observation structure
* Observation field requirements
* Maximum observation counts
* String length limits
* Contributor ID format
* Batch ID format

Additional validation is expected as the API matures.

# Telemetry Upload Flow

The current telemetry ingestion path is approximately:

```text
Veilance Browser Extension
          |
          | multipart/form-data
          v
+-----------------------------+
| Veilance Intelligence API   |
+-----------------------------+
          |
          +--> Read telemetry upload
          |
          +--> Verify file contains data
          |
          +--> Gzip decompress
          |
          +--> Parse JSON
          |
          +--> Validate telemetry top-level fields
          |
          +--> Require wallet address
          |
          +--> Require domain name
          |
          +--> Hash domain name
          |
          +--> Check SQL deduplication key
          |
          +--> Store telemetry through SQL connector
          |
          v
      Success / Error
```

The SQL insert currently receives:

```python
sql.upload_telemetry(
    ip_address,
    raw_telemetry_data,
    client_id,
    wallet_address,
    dedupe_key
)
```

# Deduplication

The current API generates its telemetry deduplication key using the submitted domain name:

```python
dedupe_key = settings.get_hash(domain_name)
```

The API then searches for existing telemetry using:

```python
sql.find_telemetry_by_deduplication_key(dedupe_key)
```

If an existing record is returned, the upload is rejected.

This means the current implementation effectively performs **domain-based deduplication**.

For example:

```text
example.com
    |
    v
settings.get_hash("example.com")
    |
    v
dedupe key
    |
    +--> existing record -> reject
    |
    +--> no record ------> insert
```

This strategy is still under development and may change as the telemetry network evolves.

# Rate Limiting

The API uses **Flask-Limiter** with Redis-backed rate-limit storage.

The current default limit is:

```text
50 requests per second
```

Configured as:

```python
default_limits=["50 per second"]
```

Redis configuration is loaded through:

```python
conf = settings.load_conf()
```

and the limiter connects using:

```text
redis://<host>:<port>/<database>
```

with the prefix:

```text
veilance-limiter
```

---

## Rate-Limit Identity

Requests are not always limited purely by source IP.

The API first attempts to retrieve:

```text
client_id
```

For JSON requests it checks:

```python
request.get_json()
```

For non-JSON requests it checks:

```python
request.form
```

If a `client_id` exists, the API hashes it:

```python
settings.get_hash(client_id)
```

and constructs the rate-limit identity:

```text
tok:<hashed-client-id>
```

If no client ID is available, the API falls back to the request IP:

```text
ip:<client-ip>
```

Conceptually:

```text
Request
   |
   +--> client_id exists
   |       |
   |       +--> hash(client_id)
   |       |
   |       +--> tok:<hash>
   |
   +--> no client_id
           |
           +--> determine client IP
           |
           +--> ip:<address>
```

This allows Veilance clients to be rate limited independently when they provide a client identifier while retaining an IP-based fallback for requests without one.

---

# Rate-Limit Responses

When the request limit is exceeded, the API returns HTTP:

```text
429 Too Many Requests
```

with the Veilance error:

```text
Hit request rate limit
```

The handler is currently:

```python
@app.errorhandler(429)
def handler_429(_):
    return settings.build_json_report(
        None,
        is_error=True,
        error_string="Hit request rate limit"
    ), 429
```

---

# Global Error Handling

Unhandled Flask exceptions are caught by the global exception handler:

```python
@app.errorhandler(Exception)
```

The API returns HTTP:

```text
500 Internal Server Error
```

with:

```text
Internal server error
```

This intentionally avoids returning raw Python exception details to API clients.

Production deployments should still log the underlying exception internally for diagnostics and monitoring.

# Redis

A reachable Redis instance is currently required when the limiter initializes.

The connection information is read from the Veilance configuration:

```python
conf = settings.load_conf()
```

Expected Redis configuration fields include:

```text
redis.host
redis.port
redis.database
```

The constructed storage URI is:

```python
redis://<host>:<port>/<database>
```

If Redis is unavailable or incorrectly configured, Flask-Limiter may fail to initialize correctly.

# Important Current Limitations

Several parts of the current API are intentionally incomplete.

### Authentication is not implemented

The following endpoints currently return placeholder errors:

```text
/api/v1/token/check
/api/users/v1/token/check
/api/admin/v1/token/check
/api/users/v1/register
/api/users/v1/login
/api/admin/v1/login
```

### Payouts are not implemented

```text
/api/admin/v1/payout
```

is currently a placeholder.

### Telemetry validation is minimal

Only the presence of these top-level fields is currently checked:

```text
schemaVersion
batchId
contributorId
observations
```

### Deduplication is currently domain-based

The current deduplication key is:

```python
settings.get_hash(domain_name)
```

As implemented, once a deduplication record exists for that domain hash, another upload using the same resulting key will be rejected.

This is likely to evolve into more granular replay/duplicate detection as the telemetry ingestion system develops.

# Veilance

This API is part of the **Veilance Intelligence Network**.

Veilance is a local-first browser privacy observability platform that helps users understand privacy-relevant behavior occurring inside their browser, including tracking, fingerprinting, third-party network activity, browser API access, storage activity, and related signals.

Telemetry contribution is designed to be separate from local detection. Users can choose to contribute sanitized observations to the shared Veilance intelligence network.

The browser extension is available for Chromium-based browsers through the Chrome Web Store.
